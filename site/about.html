How it works

This repository treats threat-detection rules like software: written in version control, reviewed, tested against real attacker telemetry, scored for quality, and blocked from merging when they fall below a bar they declare for themselves. This page is the method behind every number on the coverage dashboard — what is measured, how it is measured, and what it deliberately does not claim.

It is written on two levels at once. The blue blocks explain each idea in ordinary language with no security background assumed; the text around them is the precise version. Read either one, or both.

01The problem this solves

In plain English

Windows computers write down almost everything that happens on them, in files called event logs. When an attacker breaks in, they leave traces there. A detection rule is a written recipe that says: if you ever see this pattern in the logs, shout.

Anyone can write such a recipe. What almost nobody does is prove theirs works — that it catches the attack and stays quiet during ordinary Tuesday-afternoon admin work. This repository is a set of rules plus the machinery that produces that proof, automatically, every time anything changes.

In most organisations detection rules live inside a SIEM's web console: edited in a text box, deployed by whoever was on shift, with no history, no tests and no measurement. Nobody can answer the two questions that matter — does this rule still fire on the attack it was written for, and how much noise does it cost the analyst reading the queue.

Detection-as-Code is the answer software engineering already found: put the logic in git, make every change reviewable, and gate it on automated tests. This repo is a working implementation of that idea over 20 rules I wrote myself, plus the tooling that keeps them honest.

The claim being made

Not "I can write a Sigma rule." Anyone can. The claim is: every rule here is mapped to adversary behaviour, proven to fire on a real attack capture, measured for false positives against benign look-alikes, and continuously re-checked — and where a rule is bad, the number saying so is published rather than hidden.

02Vocabulary

Nothing below this point needs any term that is not defined here.

Detection rule
A written condition over log data that raises an alert when it matches. "Shout if a program starts with a scrambled command line" is a detection rule.
Sigma
A vendor-neutral YAML format for writing those rules. You write the logic once and compile it to whichever platform you run — Splunk, Sentinel, Elastic. Like writing a recipe in a universal language and having it auto-translated into any kitchen's local terms.
EVTX
The binary file format of Windows event logs. Public repositories publish EVTX captured while real attacker tooling ran, which is what makes it possible to test a rule against genuine telemetry rather than something I invented.
Event ID
Windows numbers every kind of event. 4688 = a program started. 1102 = the security log was cleared. 4697 = a service was installed. Attackers trigger these too, which is why they are worth watching — and why matching on the number alone is not a detection.
MITRE ATT&CK
The industry catalogue of adversary behaviour — tactics (the goal, e.g. Credential Access) and techniques (the method, e.g. T1003.001 LSASS Memory). Tagging rules with technique IDs is what turns a pile of rules into a coverage map. This repo validates tags against release v19.2.
False positive
The rule shouted and nothing bad had happened. This is the problem in security operations: a rule with too many false positives gets ignored, and an ignored rule might as well not exist.
Hayabusa
A fast Sigma engine that runs rules directly against EVTX files. Here it is the test harness: pytest hands it a rule and a captured attack and asserts on whether it hit. Pinned at v3.9.0.
pySigma
The Python library that parses Sigma and compiles it to backends. It does the conversion to Splunk and KQL, and — through its SQLite backend — the scoring of rules against labelled events.
CI
Continuous integration: a robot on GitHub's machines that re-runs every check on every change. If anything breaks it goes red. It is what stops "it worked on my laptop".

Four counts describe every rule's performance, and everything else is derived from them: TP (malicious event, rule fired), FP (benign event, rule fired anyway), FN (malicious event, rule stayed silent — a miss), TN (benign event, rule correctly silent).

03Where this started

In plain English

This repo did not begin in the state described on this page. It began as a normal portfolio project that looked fine from the outside, and was then audited on purpose, without mercy. Six things were wrong, and every one of them is the kind of thing that quietly makes a security project a decoration rather than a control.

All six are fixed. They are written down here rather than deleted from the history, because the interesting part of the project is not that it is tidy now — it is what it took to find out that it wasn't.

  1. The tests could pass while testing nothing. The suite needed an external engine. When that engine was missing the tests did not fail — they skipped, and the run reported success. The repository's single biggest claim was guarded by nothing at all.
    A smoke alarm that reports "all clear" when its battery has been removed.
  2. Nobody was measuring whether the rules were any good. There were 16 test cases. 15 asked "here is an attack, does it fire?". One asked "here is something harmless, does it stay quiet?" — and that one used a different kind of log entirely, so it proved nothing. There was zero evidence about false positives. For detection work that is a chef who never tastes the food.
  3. Four of the fifteen rules were not detections. They alerted whenever a given event ID appeared, with no further logic. That is not detecting anything; it is forwarding an event and making a human decide.
  4. The quality checker was switched off. Sigma's own linter was running, reporting 20 problems (two serious), and the build was configured to ignore all of them and pass.
  5. The supporting code had no safety net. ~800 lines of Python with no tests, no type checking, no dependency locking — in a repository whose entire pitch is treating security content like professional software.
  6. The compiled output would not have run anywhere. Rules were auto-translated to Splunk and checked for grammar, but not for whether the result was usable: wrong field names, and no statement of which logs to search. Grammatically valid nonsense.

Things measurement found that reading could not

Two examples, both invisible until there were numbers.

A real evasion. PowerShell accepts -e as an abbreviation of -EncodedCommand. The rule looked for the longer spellings only, so powershell -e <blob> walked straight past it. Fixing it moved recall from 0.80 to 1.00 and cost one false positive out of seven benign cases — and the harness blocked the change until that trade was written down.

A rule that had silently stopped running. Writing a rule's condition across multiple YAML lines is accepted by two of the three engines involved and rejected by the third, which reports only "1 parsing error" without naming the rule. The rule stops running and nothing says so. There is now a check for exactly that.

04The pipeline

In plain English

Six stages take a rule from an idea to the published map. Each one can stop the whole thing, and one command runs all of them the same way the robot does — so "it works on my machine" and "the build is green" mean the same sentence.

01Authordetections/*.yml

A Sigma rule with required metadata and ATT&CK tags. detkit probe runs the draft against real samples before it is finalised.

02Gatedetkit validate

Metadata, tag vocabulary pinned to an ATT&CK release, and a fixture or a declared exemption. Structural problems die here.

03Prove it firespytest

Hayabusa runs the rule against pinned public EVTX. Real channel, real field names, real attacker artefacts.

04Score itdetkit eval

The rule is compiled to SQL and run over hand-labelled malicious and benign events. Precision, recall and FP rate fall out of the result.

05Compiledetkit convert

Splunk SPL and Microsoft XDR KQL, with every query checked for a bound source=.

06Publishdetkit dashboard

Coverage map, Navigator layer, this site and the README table — all regenerated and diffed, so published numbers cannot go stale.

Why the order matters

Each stage assumes the previous one held. There is no point measuring the false-positive rate of a rule that does not parse, and no point publishing a coverage map built from rules that failed their tests. detkit ci stops at the first failure for the same reason.

05Two test layers, two different questions

In plain English

There are two completely separate ways a rule is checked here, because there are two different ways a rule can be wrong.

The first replays a real recorded attack and demands the rule fire. That catches a rule written against logs the author imagined rather than the ones Windows actually produces — the classic beginner mistake, and one that never shows up in your own tests.

The second feeds the rule hand-written examples, some attacks and some deliberately similar harmless activity, and counts what it does. A real attack recording cannot do this: it has no harmless counterpart inside it to stay quiet on.

The two engines are also a cross-check on each other. Two independent implementations of Sigma semantics agreeing on the same rule is worth more than trusting either alone; where they disagreed during development, the disagreement was the bug.

The cloud rules carry a third, weaker tier — and say so

In plain English

The Entra ID (Microsoft cloud identity) rules cannot get the first test. Nobody publishes recordings of cloud sign-in logs, because those logs are real people's names, addresses and devices — it is not a gap somebody forgot to fill, it is what privacy means for that data.

So those rules get the scoring, which is compulsory for them rather than optional, plus a check that every field they mention actually exists in Microsoft's published table layout. A rule that invents a column name cannot be built. What that still does not prove is that the rule fires in a real tenant, and the dashboard labels them schema-verified instead of tested so the difference is visible at a glance rather than buried here.

Concretely: detkit validate fails a non-EVTX rule with no case set, and detkit convert compiles each Entra rule to its real Log Analytics table (SigninLogs, AuditLogs) through the repo's own Azure Monitor pipeline, where the backend rejects any column Microsoft does not publish. ADR 0005 has the argument and the two rejected alternatives — not writing cloud rules at all, and writing them while quietly letting the fixture gate not apply.

06The metrics, and what each one hides

In plain English

Three numbers describe a rule, and they answer different questions:

Recall — of the real attacks, how many did it catch? Missing one is the expensive failure.
FP rate — of the harmless activity, how often did it shout anyway?
Precision — of everything it shouted about, how much was real?

The trap is that precision can be improved without touching the rule, just by writing more attack examples and fewer harmless ones. Recall and FP rate cannot be gamed that way, so they lead and precision trails.

Every rule card on the dashboard carries four figures. Hovering any of them shows this same arithmetic with that rule's own counts filled in.

False-positive rate — the number to read first

FP ÷ (FP + TN) — of the benign events, the share that alerted

Stable against the shape of the dataset: adding or removing malicious cases cannot change it. That is what makes it the honest headline. A rule at 1.00 fires on every benign look-alike it was given, which usually means it is matching an event ID and nothing else.

Recall — did it catch what it was written for

TP ÷ (TP + FN) — of the malicious events, the share that alerted

Also stable, for the mirror reason: it only looks at malicious events. A miss is the expensive failure mode, because an alert that never fires is indistinguishable from a quiet network. Almost every rule here declares a recall floor of 1.00 — missing a true positive is not negotiable, and the trade is paid in false positives instead.

Precision — how much of the alert queue is real

TP ÷ (TP + FP) — of everything that alerted, the share that was real

This is what an analyst actually feels on shift, and it is the one figure here that must be read with suspicion. Precision depends on the ratio of malicious to benign events, and in a case set that ratio is authored, not observed. Real estates run millions of benign events for every malicious one, so a rule scoring 0.80 here would score far lower in production. It is published because it is informative, and ranked third because it is flattering.

Why there is no accuracy figure

(TP + TN) ÷ total — not published anywhere in this repo

Accuracy is dominated by whichever malicious-to-benign ratio was authored. Write nine benign cases and one malicious one, and a rule that never fires at all scores 0.90. It would measure the dataset rather than the rule, which is precisely the failure this harness was built to avoid.

Worked example — posh_ps_obfuscated_payload_execution

5 malicious and 9 benign events are labelled for this rule. It fired on 5 of the malicious ones and 1 of the benign ones.

FP rate  = 1 ÷ (1 + 8) = 0.11
recall   = 5 ÷ (5 + 0) = 1.00
precision = 5 ÷ (5 + 1) = 0.83

How the labelled events are built

Each rule has an evals/<rule>/cases.yml holding events written by hand. Every case carries a why justifying its label, and the loader refuses a case without one — an unexplained label is an assertion, not evidence.

Benign cases must be genuine look-alikes: the same event type as the malicious ones, differing only where the rule is supposed to discriminate. A benign case whose event ID no malicious case uses is rejected, because it cannot exercise the rule's logic, and a set with no benign cases at all is refused outright — precision would be 1.00 by construction. An earlier version of this repo had exactly that problem: 15 of 16 fixtures were "expect fire", and the single negative was a different log channel, so it proved nothing.

07Every rule declares its own bar

In plain English

Rules are not equally hard. Detecting a specific hacking tool should be near perfect; detecting "someone added an antivirus exclusion" cannot be, because a system administrator does exactly the same thing for legitimate reasons and the log entry looks identical.

So each rule states, in its own file, the score it has to reach — and the build fails if it drops below it. Setting an easier bar is allowed. Setting one silently is not: without a written reason, the file is rejected. Every one of those reasons is printed below.

The defaults are strict — precision ≥ 0.90, recall = 1.00, FP rate ≤ 0.10. Anything more lenient is rejected at load time unless it carries a written justification. 16 of 20 rules currently run on a justified lenient threshold.

Some rules are hunting queries, not alerts

In plain English

Attackers scramble their PowerShell so it does not read as an attack. The obvious rule is "alert when a script looks scrambled" — and measuring it showed that two thirds of ordinary admin scripts look scrambled too, because joining text together and converting numbers are everyday operations.

Deleting the rule would be wrong: scrambling really is a signal. So it was demoted. It now ranks script blocks for a human to look through — a hunting query — while a second rule pages someone only when scrambling appears together with something that runs or downloads the result. Same signal, two products, two severities.

ruleasksseverityFP rate
posh_ps_susp_encoded_powershell_scriptblock which script blocks are worth a human's attention? informational0.67
posh_ps_obfuscated_payload_execution which ones should wake someone up? high0.11

The second rule's benign cases are the first rule's false alarms, so the pair is held together by its own gate: if the alerting tier ever starts firing on -join building a file path, CI fails. On the real Invoke-Obfuscation capture both rules see the same 66 script blocks; the hunting tier flags most of them, the alerting tier flags the one that also calls iex.

A false-positive rate of 0.67 is a failure for an alert and perfectly reasonable for a hunt, which is why the threshold is a property of the rule rather than a constant. Severity follows what is being obfuscated, not the fact that something is.

08What CI actually checks

In plain English

Every one of the checks below runs on every change, on GitHub's machines, and any single one of them can stop the change from landing. The last row is the unusual one: the robot rebuilds every published chart, table and page from scratch and compares them to what is committed. If they differ, someone changed a rule without refreshing the numbers, and the build fails.

One command runs all of it: uv sync --all-extras && uv run detkit ci, about twenty seconds from a clean checkout. The workflow runs the same steps split across parallel jobs.

The gate that mattered most

The suite originally passed while testing nothing: with no Hayabusa binary present every detection test skipped, and pytest exits 0 on a fully skipped run. CI now installs a checksum-verified pinned binary and treats any skip as a failure. A test suite that cannot fail is worse than no test suite, because it manufactures confidence.

09Design decisions on record

In plain English

Every significant choice is written down with the options that were considered and the reason one won — including the ones that were rejected. Knowing when not to add something is half of engineering, and it is invisible unless you record it.

  • ADR 0001 — Hayabusa for detection testing
    Hayabusa is the EVTX test engine: one static binary that runs Sigma against real event logs, driven by pytest.
  • ADR 0002 — Fetch pinned public EVTX samples instead of vendoring them
    Samples are not vendored. Each fixture pins public EVTX by repo, commit, path and SHA-256, and they are fetched and hash-verified at test time.
  • ADR 0003 — Evaluate rules over labelled JSON events with the pySigma SQLite backend
    Labelled events are evaluated through pySigma's SQLite backend rather than a second log platform. Zircolite was the obvious candidate and was rejected: it is not on PyPI, so it could not be locked. Hayabusa stays as an independent second engine and the two must agree.
  • ADR 0004 — Reproducibility without Terraform
    No Terraform. Terraform with no infrastructure behind it is a prop; reproducibility here means a clean checkout produces an identical verified run, which locked dependencies and a checksum-pinned engine already deliver.
  • ADR 0005 — Evidence tiers: how a cloud rule is proven when no capture exists
    Cloud rules carry a declared, weaker evidence tier. Nobody publishes captures of Entra ID telemetry — it is real people's tenant data — so those rules cannot be replayed against a recording. Instead their labelled scoring is mandatory and every field is validated against Microsoft's published table schema at compile time. The dashboard badges them differently rather than letting the distinction blur.
  • ADR 0006 — Severity follows the payload: a hunting tier and an alerting tier
    Obfuscation is split into two rules instead of one. Matching obfuscation primitives alone fires on two thirds of ordinary admin PowerShell (measured), so that rule is informational and used for hunting; a second rule requiring obfuscation plus an execution or download sink alerts at high, and its benign cases are the first rule's false alarms. Severity follows what is obfuscated, not that something is.
  • ADR 0007 — Closing the corpus: what this project does not do next
    The corpus is closed at its current size. More cloud rules would repeat a solved pattern rather than prove anything new, and a Splunk container replaying the same pinned EVTX would restate gates that already pass — what a live SIEM would really add is production volume, which this project does not have. Both are declined in writing rather than left on an open TODO list.

Other choices worth stating

  • The third-party corpus is demoted, not deleted. A pinned copy of the public SigmaHQ Windows corpus (2,399 rules, 100% convert rate) is run through the same conversion pipeline and contributes 288 further techniques to the map — but it is reported separately and held to none of the fixture or eval gates. Folding it into the headline would turn 20 authored rules into a four-figure number that means nothing. The headline is deliberately the smaller, true number.
  • Published artifacts are diffed, not trusted. Every generated file is rebuilt in CI and compared to what is committed. There is no ratchet file and no manual metric anywhere: if a rule changes and the numbers move, the build fails until the new numbers are committed deliberately.
  • Bad results stay published. Rules that score badly are either fixed with discriminators, reclassified with a written argument, or left visible with their real numbers. Deleting an inconvenient measurement is the one move that would make this whole repo worthless.

10Honest limits

In plain English

Everything below is a genuine weakness, written here on purpose. A limitation somebody else discovers reads very differently from one you documented yourself.

What this does not prove

  • The labelled events are synthetic. They are written to be realistic look-alikes, but they are mine. They establish that a rule's logic discriminates; they cannot establish what its volume would be on a real estate.
  • Case sets are small. 172 events across 20 rules. Enough to catch a rule that matches an event ID and nothing else — not enough for a confidence interval.
  • Some rules are irreducibly noisy, and stay. Clearing the event log is one event with no distinguishing fields; its case set scores an FP rate of 1.00 and it is still shipped at high, on a base-rate argument — the behaviour is rare enough in practice that the alert is worth the noise. Others were demoted to informational instead, so they remain available for hunting without paging anyone. Both calls are argued in the case files rather than hidden by deleting the rule.
  • Sentinel's SecurityEvent schema has no PreAuthType column, so the Kerberos rules cannot bind there without EventData parsing. KQL conversion therefore targets Microsoft XDR on the process-creation subset. That is a platform limit, documented rather than pretended away.
  • The cloud rules are not proven against a real tenant. Entra ID telemetry has no public captures, so those four rules carry the schema-verified tier described above: measured logic and a validated query, but no replay. That is a real difference from the Windows rules and it is labelled as one everywhere it appears.
  • Deployment is a static site. Nothing here provisions a SIEM. The rules compile to deployable, source-bound queries; actually running them in an estate is out of scope, and Terraform with nothing behind it would be set dressing.

12Questions this invites

Why measure detections at all — isn't a rule either right or wrong?
No. Every detection is a trade between missing the attack and drowning the analyst, and the trade is different for every behaviour. Without measurement that trade is made by whoever wrote the rule, silently, and re-made every time someone edits it. Numbers make it a decision.
Why is FP rate the headline instead of precision?
Because precision moves with the malicious-to-benign ratio of the dataset, and in a hand-authored case set I choose that ratio. FP rate looks only at benign events, so I cannot flatter it by writing more attacks. When a metric can be improved by editing the test data rather than the rule, it should not lead.
You have rules with an FP rate of 1.00. Why ship them?
Because the alternative is worse. Clearing the security event log produces one event with nothing in it to discriminate on — any rule for it fires on every instance, benign or not. What matters is the base rate: it almost never happens legitimately, so the alert is cheap in practice even though it is undiscriminating in the lab. That argument is written into the case file, and rules where the argument does not hold were demoted to informational instead.
Why two engines rather than one?
They answer different questions and check each other. Hayabusa proves a rule works against real Windows telemetry — right channel, right field names. The SQL evaluator scores the logic over labelled events, which real captures cannot do, because a capture has no benign counterfactual in it. Where two independent implementations of Sigma disagree about the same rule, something is wrong and I want the build to say so.
What stops the published numbers going stale?
CI regenerates every artifact and diffs it against what is committed. Generator output is a pure function of the corpus, so a diff means the repo changed and the published numbers no longer describe it. That includes this page.
What was actually hard?
Making failure possible. The first version of this repo passed its build while testing nothing, reported coverage it did not have, and had exactly one negative test case — which was for a different log channel and could never have failed. Most of the engineering since has been removing ways for the build to be green without being true.
Only 20 rules? SigmaHQ has thousands.
A pinned copy of SigmaHQ's Windows corpus is in this repository too, and it is reported separately on purpose. The authored rules are the ones held to every gate: a pinned capture or a mandatory case set, a declared threshold with a written justification, a bound query, an ATT&CK tag that resolves. 20 rules that each carry that evidence say more about how someone works than a thousand copied ones. The corpus is deliberately the smaller, true number.
Is this finished, or abandoned?
Finished, and the boundary is argued rather than implied — ADR 0007 names the two things that were on the list and declines both: more cloud rules of a shape already proven four times over, and a Splunk container replaying the same pinned captures the existing gates already check. What a live SIEM would genuinely add is behaviour under production volume, which is not available here, so shipping one would produce a screenshot rather than evidence. The gates keep running; the corpus is closed.
